Stash Studio API (1.0.0)

Download OpenAPI specification:

API Support: help@stash.gg URL: https://docs.stash.gg/

APIs for querying a shop's managed product catalog and loyalty program, for configuring the loyalty program from a partner's own tools, for asking Stash to refresh a shop's localizations, and for listing a shop's daily transaction files and downloading them through signed links. Designed for server-to-server communication between partner backends and Stash services.

Base URLs

Environment Base URL
Test https://test-api.stash.gg
Production https://api.stash.gg

All endpoint paths below are relative to the base URL. For example, to list products in the test environment:

GET https://test-api.stash.gg/sdk/studio/{shop_id}/products

Authentication

Every request is signed with your Ingress API key (HMAC-SHA256). Send the signature in the versioned x-stash-hmac-signature header.

Setup

  1. Go to Stash Studio > Project Settings > API Secrets
  2. Click Generate Secret to create a new key
  3. Keys created through this portal are Ingress keys by default and work with this API (this is the same key used for /sdk/ API authentication)
  4. Copy the key and store it securely; you will need it to sign every request. Studio shows the key Base64-encoded: keep it as shown, and Base64-decode it to raw bytes when you sign

Signing a Request

  1. Take the current time as a Unix timestamp in milliseconds, for example 1790000000000
  2. Build the string to sign as {timestamp}.{body}. For GET requests {body} is empty. For PUT and POST requests it is the request body exactly as you send it (the same bytes; do not re-serialize the JSON after signing). Stash verifies the signature against those exact bytes for bodies up to 18 KiB (18,432 bytes); a larger body may be refused with 401 even when it is correctly signed
  3. Base64-decode your Ingress API key to raw bytes, compute HMAC-SHA256 of that string keyed with those bytes, and Base64-encode the result. Signing with the encoded key text produces a signature Stash rejects
  4. Send the header x-stash-hmac-signature: v1;{shopId};{timestamp};{base64Signature}. The timestamp must be within 5 minutes of Stash server time

Example (bash and python)

Keep the key, exactly as Studio shows it, in a file with owner-only permissions or in a secret store, and read and Base64-decode it inside the signing process. Never pass it as a command-line argument: process listings and shell history can capture it.

# sign <body>: prints the header value for the exact body you are about to
# send. Every request gets its own timestamp and signature.
sign() {
  local ts sig
  ts=$(($(date +%s) * 1000))
  sig=$(TS="$ts" BODY="$1" python3 - <<'PY'
import base64, hashlib, hmac, os
key = base64.b64decode(open(os.path.expanduser('~/.stash/ingress-key'), 'rb').read().strip())
msg = (os.environ['TS'] + '.' + os.environ['BODY']).encode()
print(base64.b64encode(hmac.new(key, msg, hashlib.sha256).digest()).decode())
PY
)
  printf 'v1;%s;%s;%s' '{shop_id}' "$ts" "$sig"
}

# GET: the signed body is the empty string.
curl -H "x-stash-hmac-signature: $(sign '')" \
  "https://test-api.stash.gg/sdk/studio/{shop_id}/products"

# PUT: sign the exact bytes you send, then send them with --data-binary,
# which keeps them intact. -d @file strips newlines, so the server would
# see different bytes from the ones you signed and reject the signature.
BODY='{"campaign":{"id":"season-1","name":"Season 1","tiers":[]}}'
curl -X PUT -H "Content-Type: application/json" \
  -H "x-stash-hmac-signature: $(sign "$BODY")" \
  --data-binary "$BODY" \
  "https://test-api.stash.gg/sdk/studio/{shop_id}/loyalty/config"

Legacy header (deprecated)

stash-hmac-signature carries an untimestamped Base64 HMAC-SHA256 of the body alone (empty string for GET). Only four read endpoints still accept it: GET /sdk/studio/{shop_id}/products, GET /sdk/studio/{shop_id}/products/{product_id}, GET /sdk/studio/{shop_id}/loyalty and GET /sdk/studio/{shop_id}/loyalty/players/{player_id}. It is replayable, so use the versioned header for new integrations. Every other endpoint accepts only the versioned header and answers 401 to the legacy one.

Configure a loyalty season

Creates or updates one loyalty campaign (season) together with the shop-level display settings, bonus definitions, reward products and spend conversion table it depends on, and optionally activates the program. The campaign id is the upsert key: an existing id updates that season, a new id creates one. The request describes the whole season it names, so a tier or milestone omitted from it is removed from that season; bonuses and reward products are created or updated by id or SKU and never removed. Draft and scheduled seasons accept every change. An active season accepts names, descriptions, images, milestone rewards, tier earn rates and a new end date; thresholds, adding or removing tiers or milestones, the start date and reset rules are refused with FAILED_PRECONDITION listing the fields. Ended seasons are read-only. This method accepts only the versioned x-stash-hmac-signature header, signed over the request body exactly as sent; the legacy stash-hmac-signature header is rejected with UNAUTHENTICATED, because it carries no timestamp and a captured request could be replayed. Applying is idempotent: after a 500, resend the same request. Returns INVALID_ARGUMENT with per-field violations when validation fails, FAILED_PRECONDITION also when the shop's loyalty program is bound to more than one shop, PERMISSION_DENIED when the shop is not enabled for configuration writes, ABORTED when another update for the shop is in progress, and NOT_FOUND for an unknown shop.

Authorizations:
hmac
path Parameters
shopId
required
string

Shop identifier from Stash Studio

Request Body schema: application/json
required
activate
boolean

Turn the program on once the request has been applied and passes publish validation. Honoured only on a program that has never been published; ignored otherwise and reported in warnings. A program unpublished in Studio stays off until it is re-enabled in Studio, so a sync cannot undo a deliberate stop. Creates the program for the shop if it has none.

object (Loyalty Display Config)

Shop-level display settings, overwritten as sent: a field left out of the object is cleared. Omit the whole object to leave the settings unchanged.

Array of objects (Loyalty Bonus Definition)

Bonus definitions, created or updated by id. A bonus missing from the list is left in place; the API never deletes bonuses because wallet balances depend on them.

Array of objects (Loyalty Reward Product)

Reward products, created or updated by SKU. Every product listed is published on write, including one saved as a draft in Studio; leave a product out of the list to keep its Studio draft unpublished. A product missing from the list is left in place; the API never deletes products because claimed milestones and ended seasons still refer to them. Applied before the campaign, so a milestone may reference a SKU defined in the same request.

required
object (Loyalty Campaign Config)

The season to create or update; its id is the upsert key. The season is replaced as a whole: a tier or milestone omitted from it is removed from that season. Other seasons are not touched.

object (Loyalty Spend Conversion)

The shop's spend conversion table, which lets earning convert a purchase in a non-USD currency to its US dollar equivalent. Optional and program-level: it is not part of the season, applies whatever the season's status, and is not subject to the active-season edit lock. Sending it replaces the stored table; omitting it leaves the stored table unchanged; sending it with an empty tiers list removes the table. With a table stored, a purchase in a currency the table does not include earns no points (it is never blocked); without a table, earning is unchanged. A change reaches purchases within 30 seconds. A validation failure returns INVALID_ARGUMENT with per-field violations under spendConversion, for example spendConversion.tiers[0].prices.EUR.

Localization

Endpoints for refreshing a shop's localizations from its localization source

Refresh localizations

Asks Stash to refresh the shop's localizations from its enabled localization source, for example after the source file changes. The request body is the empty JSON object {}. This method accepts only the versioned x-stash-hmac-signature header, signed over the request body exactly as sent ({}); the legacy stash-hmac-signature header is rejected with UNAUTHENTICATED, because it carries no timestamp and a captured request could be replayed. The shop in the signature header must equal the shop_id in the path. A successful response means the refresh is durably queued, not that the import has completed or that the storefront shows the result. Repeated calls are safe, so retry after UNAVAILABLE or a timeout with a fresh timestamp and signature. Returns UNAUTHENTICATED when the signature is missing, invalid, outside the time window, sent in the legacy header, or names a different shop or one Stash does not know; FAILED_PRECONDITION when the shop has no enabled localization source; and UNAVAILABLE when the refresh could not be queued, in which case retry.

Reports

Endpoints for listing a shop's daily transaction files and downloading them through signed links

List report files

Returns one entry for each UTC day in [start_date, end_date] that has a file, in date order, each with a signed GET link to that day's file. A day with no transactions still has a file, with no rows. A day with no entry is a day the export has not written yet, such as the current UTC day or a day whose export is late; it does not mean the day had no transactions, so call again later for that day. The files are the transaction report files that Stash Studio offers for the shop. Each row is one event: a payment, a refund or a dispute step. A later refund or dispute step is a new row on its own day; it does not change the payment's row. The first column, record_id, is a stable ID of the event: the same event has the same record_id in every file. Use it to remove rows that two pulls share, and keep the row from the later pull. Columns are added only at the end, and a column is renamed or removed only with advance notice, so read the files by column name, not by position. A day that is not final can still change; pull it again until is_final is true. Every link is valid until download_url_expires_at, 15 minutes after the response; call again for fresh links. This method accepts only the versioned x-stash-hmac-signature header, signed over the request body exactly as sent; the legacy stash-hmac-signature header is rejected with UNAUTHENTICATED, because it carries no timestamp and a captured request could be replayed. The shop in the signature header must equal the shop_id in the path. Repeated calls are safe, so retry after UNAVAILABLE or a timeout with a fresh timestamp and signature. Returns UNAUTHENTICATED when the signature is missing, invalid, outside the time window, sent in the legacy header, or names a different shop or one Stash does not know; INVALID_ARGUMENT when report_type or report_format is unspecified or unknown, a date is missing or is not YYYY-MM-DD, end_date is before start_date, or the range is longer than 31 days; and UNAVAILABLE when the files could not be listed, in which case retry.
