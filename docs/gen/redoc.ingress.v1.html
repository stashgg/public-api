Stash Studio API (1.0.0)

Download OpenAPI specification:

API Support: help@stash.gg URL: https://docs.stash.gg/

APIs for querying a shop's managed product catalog and loyalty program, for configuring the loyalty program from a partner's own tools, for asking Stash to refresh a shop's localizations, and for pulling a shop's Financial Report rows. Designed for server-to-server communication between partner backends and Stash services.

Base URLs

Environment Base URL
Test https://test-api.stash.gg
Production https://api.stash.gg

All endpoint paths below are relative to the base URL. For example, to list products in the test environment:

GET https://test-api.stash.gg/sdk/studio/{shop_id}/products

Authentication

Every request is signed with your Ingress API key (HMAC-SHA256). Send the signature in the versioned x-stash-hmac-signature header.

Setup

  1. Go to Stash Studio > Project Settings > API Secrets
  2. Click Generate Secret to create a new key
  3. Keys created through this portal are Ingress keys by default and work with this API (this is the same key used for /sdk/ API authentication)
  4. Copy the key and store it securely; you will need it to sign every request. Studio shows the key Base64-encoded: keep it as shown, and Base64-decode it to raw bytes when you sign

Signing a Request

  1. Take the current time as a Unix timestamp in milliseconds, for example 1790000000000
  2. Build the string to sign as {timestamp}.{body}. For GET requests {body} is empty. For PUT and POST requests it is the request body exactly as you send it (the same bytes; do not re-serialize the JSON after signing). Stash verifies the signature against those exact bytes for bodies up to 18 KiB (18,432 bytes); a larger body may be refused with 401 even when it is correctly signed
  3. Base64-decode your Ingress API key to raw bytes, compute HMAC-SHA256 of that string keyed with those bytes, and Base64-encode the result. Signing with the encoded key text produces a signature Stash rejects
  4. Send the header x-stash-hmac-signature: v1;{shopId};{timestamp};{base64Signature}. The timestamp must be within 5 minutes of Stash server time

Example (bash and python)

Keep the key, exactly as Studio shows it, in a file with owner-only permissions or in a secret store, and read and Base64-decode it inside the signing process. Never pass it as a command-line argument: process listings and shell history can capture it.

# sign <body>: prints the header value for the exact body you are about to
# send. Every request gets its own timestamp and signature.
sign() {
  local ts sig
  ts=$(($(date +%s) * 1000))
  sig=$(TS="$ts" BODY="$1" python3 - <<'PY'
import base64, hashlib, hmac, os
key = base64.b64decode(open(os.path.expanduser('~/.stash/ingress-key'), 'rb').read().strip())
msg = (os.environ['TS'] + '.' + os.environ['BODY']).encode()
print(base64.b64encode(hmac.new(key, msg, hashlib.sha256).digest()).decode())
PY
)
  printf 'v1;%s;%s;%s' '{shop_id}' "$ts" "$sig"
}

# GET: the signed body is the empty string.
curl -H "x-stash-hmac-signature: $(sign '')" \
  "https://test-api.stash.gg/sdk/studio/{shop_id}/products"

# PUT: sign the exact bytes you send, then send them with --data-binary,
# which keeps them intact. -d @file strips newlines, so the server would
# see different bytes from the ones you signed and reject the signature.
BODY='{"campaign":{"id":"season-1","name":"Season 1","tiers":[]}}'
curl -X PUT -H "Content-Type: application/json" \
  -H "x-stash-hmac-signature: $(sign "$BODY")" \
  --data-binary "$BODY" \
  "https://test-api.stash.gg/sdk/studio/{shop_id}/loyalty/config"

Legacy header (deprecated)

stash-hmac-signature carries an untimestamped Base64 HMAC-SHA256 of the body alone (empty string for GET). The catalog and loyalty read endpoints still accept it, but it is replayable, so use the versioned header for new integrations. The configuration write, PUT /sdk/studio/{shop_id}/loyalty/config, the localization refresh, POST /sdk/studio/{shop_id}/localizations/refresh, and the transaction records, GET /sdk/studio/{shop_id}/transactions, accept only the versioned header and answer 401 to the legacy one.

Configure a loyalty season

Creates or updates one loyalty campaign (season) together with the shop-level display settings, bonus definitions and reward products it depends on, and optionally activates the program. The campaign id is the upsert key: an existing id updates that season, a new id creates one. The request describes the whole season it names, so a tier or milestone omitted from it is removed from that season; bonuses and reward products are created or updated by id or SKU and never removed. Draft and scheduled seasons accept every change. An active season accepts names, descriptions, images, milestone rewards, tier earn rates and a new end date; thresholds, adding or removing tiers or milestones, the start date and reset rules are refused with FAILED_PRECONDITION listing the fields. Ended seasons are read-only. This method accepts only the versioned x-stash-hmac-signature header, signed over the request body exactly as sent; the legacy stash-hmac-signature header is rejected with UNAUTHENTICATED, because it carries no timestamp and a captured request could be replayed. Applying is idempotent: after a 500, resend the same request. Returns INVALID_ARGUMENT with per-field violations when validation fails, FAILED_PRECONDITION also when the shop's loyalty program is bound to more than one shop, PERMISSION_DENIED when the shop is not enabled for configuration writes, ABORTED when another update for the shop is in progress, and NOT_FOUND for an unknown shop.

Authorizations:
hmac
path Parameters
shopId
required
string

Shop identifier from Stash Studio

Request Body schema: application/json
required
activate
boolean

Turn the program on once the request has been applied and passes publish validation. Honoured only on a program that has never been published; ignored otherwise and reported in warnings. A program unpublished in Studio stays off until it is re-enabled in Studio, so a sync cannot undo a deliberate stop. Creates the program for the shop if it has none.

object (Loyalty Display Config)

Shop-level display settings, overwritten as sent: a field left out of the object is cleared. Omit the whole object to leave the settings unchanged.

Array of objects (Loyalty Bonus Definition)

Bonus definitions, created or updated by id. A bonus missing from the list is left in place; the API never deletes bonuses because wallet balances depend on them.

Array of objects (Loyalty Reward Product)

Reward products, created or updated by SKU. Every product listed is published on write, including one saved as a draft in Studio; leave a product out of the list to keep its Studio draft unpublished. A product missing from the list is left in place; the API never deletes products because claimed milestones and ended seasons still refer to them. Applied before the campaign, so a milestone may reference a SKU defined in the same request.

required
object (Loyalty Campaign Config)

The season to create or update; its id is the upsert key. The season is replaced as a whole: a tier or milestone omitted from it is removed from that season. Other seasons are not touched.

Localization

Endpoints for refreshing a shop's localizations from its localization source

Refresh localizations

Asks Stash to refresh the shop's localizations from its enabled localization source, for example after the source file changes. The request body is the empty JSON object {}. This method accepts only the versioned x-stash-hmac-signature header, signed over the request body exactly as sent ({}); the legacy stash-hmac-signature header is rejected with UNAUTHENTICATED, because it carries no timestamp and a captured request could be replayed. The shop in the signature header must equal the shop_id in the path. A successful response means the refresh is durably queued, not that the import has completed or that the storefront shows the result. Repeated calls are safe, so retry after UNAVAILABLE or a timeout with a fresh timestamp and signature. Returns UNAUTHENTICATED when the signature is missing, invalid, outside the time window, sent in the legacy header, or names a different shop or one Stash does not know; FAILED_PRECONDITION when the shop has no enabled localization source; and UNAVAILABLE when the refresh could not be queued, in which case retry.

Transactions

Endpoint for pulling a shop's Financial Report rows

List transaction records

Lists the rows of the shop's Financial Report, the settled-transaction report you reconcile payouts against, for a time window. Each record is one report row, with that row's meaning, signs and settlement dating, so the totals of the records equal the report and the payout. Join records to your purchases by transaction_id; upsert them by record_id. One transaction_id can have several payment records: failed attempts before a successful one, and rarely a second successful payment. A purchase that Stash granted can have no successful payment record when the capture failed after the grant. Set start_at and end_at (RFC 3339) to the window [start_at, end_at): start_at is inclusive, end_at is exclusive, end_at must be later than start_at, and the window is at most 31 days. A record is in the window when its ts is. An end_at later than available_until is accepted: the response then covers [start_at, available_until), and you pull again later from available_until. Records are ordered by ts, then record_id. To read all records of a window, send next_page_token as page_token, with the same start_at and end_at, until next_page_token is absent. Each page reports its as_of. as_of identifies one snapshot of the shop's report data, and one snapshot covers every month, final and preliminary. Every page of one walk comes from the snapshot of its first page, because the page_token carries it. If Stash rebuilds the report during a walk, the next page request returns ABORTED. Then start the window again from the first page, without page_token, and delete no record because of that walk. An empty window returns an empty records list, not an error. A record is final when the final report for its period exists; Stash generates it on day 5 of the next month (UTC). A final record never changes. A preliminary record (final is false) can change or disappear without a notice. On every re-pull, replace all preliminary records of the pulled window with what the response returns, and upsert the others by record_id. Re-pull a window until day 5 (UTC) of the month after the window's last month has passed and the final reports exist, whatever the window returned; then pull it one last time. On each record, merchant.payout = merchant.amount - merchant.channel_fees - merchant.tax - merchant.stash_fee + merchant.stash_fee_waived. The deductions are positive when charged on the row and negative when credited back, so subtract them as they are; do not change their signs, and do not filter records by sign. Add amounts only within one merchant.currency. This method accepts only the versioned x-stash-hmac-signature header, signed over the empty body because this is a GET request; the legacy stash-hmac-signature header is rejected with UNAUTHENTICATED, because it carries no timestamp and a captured request could be replayed. The shop in the signature header must equal the shop_id in the path. Returns UNAUTHENTICATED when the signature is missing, invalid, outside the 5-minute time window, sent in the legacy header, or names a different shop or one Stash does not know; INVALID_ARGUMENT for a missing or malformed start_at or end_at, an end_at that is not later than start_at, a window longer than 31 days, a limit outside 1 to 100, a malformed page_token, or a page_token sent with a different window; ABORTED when Stash rebuilt the report after the page_token was issued, in which case start the window again from the first page without page_token, because a retry with the same page_token fails again; and UNAVAILABLE when the data cannot be read, in which case retry with a fresh timestamp and signature.

Shop identifier from Stash Studio. Must equal the shop in the x-stash-hmac-signature header.

query Parameters
startAt
required
string <date-time>

Start of the window, inclusive (RFC 3339). Compared with each record's ts.

endAt
required
string <date-time>

End of the window, exclusive (RFC 3339). Must be later than start_at and at most 31 days after it. A value later than available_until is accepted; the response then covers [start_at, available_until).

limit
integer <int64>

Maximum records per page. Defaults to 50. Maximum allowed value is 100.

pageToken
string

Opaque token from next_page_token of the previous response. Omit it on the first page. It carries the window, the position and the snapshot of the walk's first page, so send the same start_at and end_at with it. Do not parse or build it.
