Stash Studio API (1.0.0)

Download OpenAPI specification:

API Support: help@stash.gg URL: https://docs.stash.gg/

APIs for querying a shop's managed product catalog and loyalty program, for configuring the loyalty program from a partner's own tools, and for asking Stash to refresh a shop's localizations. Designed for server-to-server communication between partner backends and Stash services.

Base URLs

Environment Base URL
Test https://test-api.stash.gg
Production https://api.stash.gg

All endpoint paths below are relative to the base URL. For example, to list products in the test environment:

GET https://test-api.stash.gg/sdk/studio/{shop_id}/products

Authentication

Every request is signed with your Ingress API key (HMAC-SHA256). Send the signature in the versioned x-stash-hmac-signature header.

Setup

  1. Go to Stash Studio > Project Settings > API Secrets
  2. Click Generate Secret to create a new key
  3. Keys created through this portal are Ingress keys by default and work with this API (this is the same key used for /sdk/ API authentication)
  4. Copy the key and store it securely; you will need it to sign every request. Studio shows the key Base64-encoded: keep it as shown, and Base64-decode it to raw bytes when you sign

Signing a Request

  1. Take the current time as a Unix timestamp in milliseconds, for example 1790000000000
  2. Build the string to sign as {timestamp}.{body}. For GET requests {body} is empty. For PUT and POST requests it is the request body exactly as you send it (the same bytes; do not re-serialize the JSON after signing). Stash verifies the signature against those exact bytes for bodies up to 18 KiB (18,432 bytes); a larger body may be refused with 401 even when it is correctly signed
  3. Base64-decode your Ingress API key to raw bytes, compute HMAC-SHA256 of that string keyed with those bytes, and Base64-encode the result. Signing with the encoded key text produces a signature Stash rejects
  4. Send the header x-stash-hmac-signature: v1;{shopId};{timestamp};{base64Signature}. The timestamp must be within 5 minutes of Stash server time

Example (bash and python)

Keep the key, exactly as Studio shows it, in a file with owner-only permissions or in a secret store, and read and Base64-decode it inside the signing process. Never pass it as a command-line argument: process listings and shell history can capture it.

# sign <body>: prints the header value for the exact body you are about to
# send. Every request gets its own timestamp and signature.
sign() {
  local ts sig
  ts=$(($(date +%s) * 1000))
  sig=$(TS="$ts" BODY="$1" python3 - <<'PY'
import base64, hashlib, hmac, os
key = base64.b64decode(open(os.path.expanduser('~/.stash/ingress-key'), 'rb').read().strip())
msg = (os.environ['TS'] + '.' + os.environ['BODY']).encode()
print(base64.b64encode(hmac.new(key, msg, hashlib.sha256).digest()).decode())
PY
)
  printf 'v1;%s;%s;%s' '{shop_id}' "$ts" "$sig"
}

# GET: the signed body is the empty string.
curl -H "x-stash-hmac-signature: $(sign '')" \
  "https://test-api.stash.gg/sdk/studio/{shop_id}/products"

# PUT: sign the exact bytes you send, then send them with --data-binary,
# which keeps them intact. -d @file strips newlines, so the server would
# see different bytes from the ones you signed and reject the signature.
BODY='{"campaign":{"id":"season-1","name":"Season 1","tiers":[]}}'
curl -X PUT -H "Content-Type: application/json" \
  -H "x-stash-hmac-signature: $(sign "$BODY")" \
  --data-binary "$BODY" \
  "https://test-api.stash.gg/sdk/studio/{shop_id}/loyalty/config"

Legacy header (deprecated)

stash-hmac-signature carries an untimestamped Base64 HMAC-SHA256 of the body alone (empty string for GET). Only four read endpoints still accept it: GET /sdk/studio/{shop_id}/products, GET /sdk/studio/{shop_id}/products/{product_id}, GET /sdk/studio/{shop_id}/loyalty and GET /sdk/studio/{shop_id}/loyalty/players/{player_id}. It is replayable, so use the versioned header for new integrations. Every other endpoint accepts only the versioned header and answers 401 to the legacy one.

Get loyalty configuration

Retrieves the shop's loyalty configuration in the shape UpdateLoyaltyConfig accepts: display settings, bonus definitions, reward products with their status, every campaign (season) with its status, and the spend conversion table with the rate derived per currency. Product rewards are returned by SKU. Use it to verify a sync. This method accepts only the versioned x-stash-hmac-signature header, signed over an empty body; the legacy stash-hmac-signature header is rejected with HTTP 401 (UNAUTHENTICATED), because it carries no timestamp and a captured request could be replayed. Errors, by the HTTP status a REST caller receives and its gRPC status: 401 UNAUTHENTICATED when the signature is missing, invalid, outside the time window, sent in the legacy header, or names a different shop; fix the signing, because resending it unchanged does not help. 404 NOT_FOUND for an unknown shop or a shop with no loyalty program; it does not change on a retry. 501 UNIMPLEMENTED when the loyalty configuration API is not available; it does not change on a retry. 500 INTERNAL when Stash could not read the configuration; reading is safe to repeat, so retry with backoff.

Configure a loyalty season

Creates or updates one loyalty campaign (season) together with the shop-level display settings, bonus definitions and reward products it depends on, optionally sets or removes the program-level spend conversion table, and optionally activates the program. The campaign id is the upsert key: an existing id updates that season, a new id creates one. The request describes the whole season it names, so a tier or milestone omitted from it is removed from that season; bonuses and reward products are created or updated by id or SKU and never removed. Draft and scheduled seasons accept every change. An active season accepts names, descriptions, images, milestone rewards, tier earn rates and a new end date; thresholds, adding or removing tiers or milestones, the start date and reset rules are refused with FAILED_PRECONDITION listing the fields. Ended seasons are read-only. This method accepts only the versioned x-stash-hmac-signature header, signed over the request body exactly as sent; the legacy stash-hmac-signature header is rejected with HTTP 401 (UNAUTHENTICATED), because it carries no timestamp and a captured request could be replayed. Applying is idempotent, so resending the same request is safe. Errors, by the HTTP status a REST caller receives and its gRPC status. Two of them share HTTP 400; a REST caller tells them apart by the code in the error body, 3 for INVALID_ARGUMENT and 9 for FAILED_PRECONDITION. 400 INVALID_ARGUMENT (code 3) with per-field violations when validation fails; fix the request, because resending it unchanged does not help. 400 FAILED_PRECONDITION (code 9) when the request cannot apply to the program as it stands, with the reason in the message: for example a locked field of an active season changes (the message lists the fields), the shop has no loyalty program and activate is not set, or the shop's loyalty program is bound to more than one shop; resend only once that changes, or as is when the message says to re-send the request. 401 UNAUTHENTICATED when the signature is missing, invalid, outside the time window, sent in the legacy header, or names a different shop; fix the signing. 403 PERMISSION_DENIED when the shop is not enabled for configuration writes; it does not change on a retry. 404 NOT_FOUND for an unknown shop; it does not change on a retry. 409 ABORTED when another update for the shop is in progress; resend the same request after a short wait, which is safe because applying is idempotent. 501 UNIMPLEMENTED when the loyalty configuration API is not available; it does not change on a retry. 500 INTERNAL when the update could not be applied; resend the same request with backoff.

required
activate
boolean

Turn the program on once the request has been applied and passes publish validation. Honoured only on a program that has never been published; ignored otherwise and reported in warnings. A program unpublished in Studio stays off until it is re-enabled in Studio, so a sync cannot undo a deliberate stop. Creates the program for the shop if it has none.

object (Loyalty Display Config)

Shop-level display settings, overwritten as sent: a field left out of the object is cleared. Omit the whole object to leave the settings unchanged.

Array of objects (Loyalty Bonus Definition)

Bonus definitions, created or updated by id. A bonus missing from the list is left in place; the API never deletes bonuses because wallet balances depend on them.

Array of objects (Loyalty Reward Product)

Reward products, created or updated by SKU. Every product listed is published on write, including one saved as a draft in Studio; leave a product out of the list to keep its Studio draft unpublished. A product missing from the list is left in place; the API never deletes products because claimed milestones and ended seasons still refer to them. Applied before the campaign, so a milestone may reference a SKU defined in the same request.

required
object (Loyalty Campaign Config)

The season to create or update; its id is the upsert key. The season is replaced as a whole: a tier or milestone omitted from it is removed from that season. Other seasons are not touched.

object (Loyalty Spend Conversion)

The shop's spend conversion table, which lets earning convert a purchase in a non-USD currency to its US dollar equivalent. Optional and program-level: it is not part of the season, applies whatever the season's status, and is not subject to the active-season edit lock. Sending it replaces the stored table; omitting it leaves the stored table unchanged; sending it with an empty tiers list, or as the empty object {}, removes the table. With a table stored, the spend of a purchase in a currency the table does not include earns no points, while loyalty points the offer grants as a bonus are still earned (the purchase is never blocked); without a table, earning is unchanged. A change reaches purchases within 30 seconds. A validation failure returns INVALID_ARGUMENT with per-field violations under spendConversion, for example spendConversion.tiers[0].prices.EUR.

Localization

Endpoints for refreshing a shop's localizations from its localization source

Refresh localizations

Asks Stash to refresh the shop's localizations from its enabled localization source, for example after the source file changes. The request body is the empty JSON object {}. This method accepts only the versioned x-stash-hmac-signature header, signed over the request body exactly as sent ({}); the legacy stash-hmac-signature header is rejected with HTTP 401 (UNAUTHENTICATED), because it carries no timestamp and a captured request could be replayed. The shop in the signature header must equal the shop_id in the path. A successful response means the refresh is durably queued, not that the import has completed or that the storefront shows the result. Repeated calls are safe, so retry after a 500, a 503 or a timeout with a fresh timestamp and signature. Errors, by the HTTP status a REST caller receives and its gRPC status. Two of them share HTTP 400; a REST caller tells them apart by the code in the error body, 3 for INVALID_ARGUMENT and 9 for FAILED_PRECONDITION. 400 INVALID_ARGUMENT (code 3) when the request is malformed, for example a body that is not valid JSON; fix the request, because resending it unchanged does not help. 400 FAILED_PRECONDITION (code 9) when the shop has no enabled localization source; retrying does not help until the source is set up and enabled. 401 UNAUTHENTICATED when the signature is missing, invalid, outside the time window, sent in the legacy header, or names a different shop or one Stash does not know; fix the signing, because resending it unchanged does not help. 500 INTERNAL when Stash could not read the shop's localization settings; retry with backoff. 503 UNAVAILABLE when the refresh could not be queued; retry with backoff.
